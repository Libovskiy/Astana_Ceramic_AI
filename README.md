# ACAI — цифровой помощник завода

> ИИ-ассистенту: сначала прочитай [`AI_CONTEXT.md`](AI_CONTEXT.md) — там устройство системы, правила и известные грабли.

FastAPI + SQLite + Jinja2 (без сборки фронтенда). Веб-приложение для
цеха «Астана Керамик»: рабочий сообщает о поломке и получает разбор от
ИИ по шагам, механик и электрик ведут очередь работ, мастер смены —
обходы и выпуск, главный инженер — оборудование, документы и
регламенты, директор — сводку по заводу.

**Адрес для людей:** `https://91-147-113-239.sslip.io` — боевой сервер
в облаке (Ubuntu, systemd). Сертификат настоящий, ставить ничего не надо.

## Запуск

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env   # вписать OPENAI_API_KEY и остальные переменные

uvicorn backend.api.main:app --host 0.0.0.0 --port 8000
```

Открыть http://localhost:8000 — страница входа.

### Где это крутится

**Боевой сервер — в облаке:** `https://91-147-113-239.sslip.io`,
Ubuntu, systemd. Этот адрес и открывают на заводе.

**Мак — машина разработчика.** Автозапуски launchd на нём отключены
намеренно (плисты в `deploy/` остались как история). Локально сервер
поднимается руками:

```bash
./venv/bin/python -m uvicorn backend.api.main:app --port 8000
```

Флага `--reload` нет — после правки Python-кода перезапускайте сами.
Логи — в `logs/`.

**Ночные задачи на сервере** (crontab): 02:00 бэкап, воскресенье 03:00
бэкап с документами, 03:30 свёртка показаний датчиков, 04:00 чистка
архива сменного отчёта (заменённые загрузки старше 20 дней; без
сегодняшнего бэкапа не чистит).

**Выкладка на боевой сервер** — `rsync` на `acai:/home/acaiadmin/FactoryAssistant/`
с исключениями: база, `.env`, `docs/`, `knowledge_base/`, `uploads/`,
`data/`, `frontend/static/uploads/`, `backups/`, `certs/`, `logs/`.
Это данные, которые живут только на сервере: документы и фото люди
загружают через сайт, поисковый указатель строится там же. `--delete`
не используем, поэтому лишнего не удалится — но одноимённые файлы
перезапишутся, а этого хватит, чтобы откатить работу людей.

**Первым шагом всегда `--dry-run`** и глазами по списку. Команда
целиком и объяснение каждого исключения — в `AI_CONTEXT.md`, раздел
«Выкладка кода».

## Структура

- `backend/api/main.py` — точка входа: `ensure_schema()`, подключение
  роутеров, статика, `PAGE_ROLES` (кому какая страница открыта).
  Роутеры разбиты по областям: `backend/api/*_routes.py` (36 файлов).
- `backend/services/` — бизнес-логика (46 модулей): обращения и ответы
  ИИ, простои, аналитика, регламенты, склад, уведомления, бэкапы,
  доступность сервера. Роутеры тонкие и зовут сервисы.
- `backend/models.py`, `backend/schemas.py`, `backend/database.py` —
  модели SQLAlchemy. **Важно:** почти всё работает напрямую с
  `factory.db` через `sqlite3`, вход — по сессионной cookie
  (`backend/services/auth_service.py`). Исключение одно — показания
  датчиков: они пишутся через SQLAlchemy в **`monitoring.db`**
  (`backend/config.py: DATABASE_URL`). Это две разные базы, обе живут
  в корне и обе нужны сайту и бэкапу.
- `frontend/templates/` — Jinja2-страницы, `frontend/static/` — общие
  `acai.css`/`acai_layout.js` плюс страничные скрипты и стили.
  Сборки нет: правишь файл — бей версию в `?v=N`, иначе браузер
  отдаст старое.
- `certs/` — корневой сертификат завода, сертификат сервера и ключи
  web push (VAPID). В бэкап входит, в git — нет.
- `docs/` — файлы руководств и паспортов оборудования (сырые байты;
  метаданные и статус подтверждения — в БД). В git не попадает.
- `knowledge_base/` — векторная база (Chroma) для поиска по
  документации. В git не попадает.
- `project-docs/` — служебная документация проекта (не путать с
  `docs/`).
- `deploy/` — копии launchd-плистов для справки.
- `tools/webhmi-extension/` — расширение Chrome, которое собирает
  показания с панели WebHMI. Без него нет данных с датчиков.
  Установка по шагам, со снимками окна — `tools/webhmi-extension/
  УСТАНОВКА.md`. **Секретов в этой папке нет**: адрес системы, ключ
  датчиков и доступ к панели вводят в окне расширения, и лежат они в
  `chrome.storage.local` на заводском компьютере.
  **Версия 6 (28.09.2026) шлёт «сердцебиение» и при ошибке чтения
  панели** — по нему сервер отличает «панель не отвечает» от
  «расширение не на связи». Пока на заводском компьютере стоит версия
  5, любая беда будет подписана как «расширение не на связи»:
  расширение при ошибке просто молчало. Обновить — переустановить
  папку в Chrome.

## Роли

13 ролей, полный список и права — в `AI_CONTEXT.md` (раздел 4) и в
`PAGE_ROLES` (`backend/api/main.py`). Коротко:

`worker` (сообщает о поломке) → `mechanic` / `electrician`
(устраняют, каждый видит свою часть) → `shift_supervisor` (обходы,
выпуск, черновик закрытия) → `chief_mechanic` / `chief_electrician`
(своя дисциплина и склад) → `chief_engineer` (оборудование, документы,
структура) → `director` (сводка по заводу) → `admin` (учётные записи).
Отдельно: `technologist` (нормы и регламенты), `lab_technician`
(лаборатория), `analyst` (аналитика), `engineer`.

Два правила, которые легко нарушить:

- **Кнопка есть — значит, она работает.** Список ролей на странице и
  проверка на сервере должны совпадать; расхождение ловит
  `tests/test_buttons_match_rights.py`.
- **Удаление структуры — это архивирование** (`is_active=0`).
  Сотрудника с историей удалить нельзя, только закрыть доступ:
  история обращений, обходов и отчётов должна остаться с фамилией.

## Порядок работы

Два правила, которые стоили ошибок и поэтому записаны здесь, а не
держатся в голове.

**1. К каждой проверке «не обнуляет / не пропускает» — парная, которая
на старом коде падает.**

Зелёный тест стоит ровно столько, сколько стоит его способность
покраснеть. 28.09.2026 проверка на частичную правку вагонетки прошла
обманом: номер вагонетки был обязательным полем, частичный запрос
отлетал с 422, и утверждение «поддоны не обнулились» выполнялось само
собой — при полностью сломанном коде.

Как делать: рядом со сценарием «правка не стёрла соседние поля» ставить
сценарий, воспроизводящий старое поведение (например, вызвать службу с
полным словарём значений по умолчанию — ровно то, что делал старый
код), и утверждать, что он ДЕЙСТВИТЕЛЬНО стирает.

Это правило окупается сразу. Парная проверка к документам станка
нашла второй изъян в тот же день: уже убранный документ «удалялся»
повторно, отвечал «успешно» и оставлял в журнале вторую запись об
одном и том же.

**2. Выводы о данных — только по боевой базе и только чтением.**

Ни по своей копии, ни по локальной базе разработчика: они расходятся.
28.09.2026 учение восстановления месяцами разворачивало копию от 21
сентября вместо ночной — заметили только тогда, когда посмотрели на
боевой сервер, а не на свою машину.

Читать боевую базу можно (`sqlite3 factory.db "SELECT ..."`, доступ
только на чтение). Писать в неё из проверок и разборов — нельзя:
проверки идут в песочнице на копии, а правки боевых записей делаются
отдельным скриптом с журналом и с копией базы перед запуском.

## Проверки

```bash
./venv/bin/python tests/run_all.py     # всё сразу, ~2 мин, 33 файла
./venv/bin/python tests/test_e2e_breakdown.py   # по отдельности
```

Все работают в песочнице `tests/sandbox.py`: копия `factory.db` и
`monitoring.db` во временной папке, свои файлы, свои учётки, OpenAI
выключен. Живые данные не трогаются.

Что проверяется: сквозной путь поломки, права от обратного (все адреса
без входа и под каждой ролью), файлы и вложения, восстановление из
ночной копии, совпадение меню с правами на сервере, списание запчастей
по ремонту, ответы ИИ всем ролям, читаемость тёмной темы, отсутствие
дублей маршрутов.

## Скрипты обслуживания (`scripts/`)

Запускаются вручную из корня (`./venv/bin/python scripts/<папка>/<файл>.py`),
кроме тех, что перечислены в таблице агентов выше:

- `scripts/admin/` — учётные записи, привязка оборудования,
  `cert_reissue.py` (сертификат) и `mdns_alias.py` (имя `acai.local`).
- `scripts/seed/` — начальные данные.
- `scripts/knowledge/` — переиндексация базы знаний, разбор документов.
- `scripts/diagnostics/` — проверки состояния и готовности к пилоту.
- `scripts/cleanup/` — разовая чистка тестовых и осиротевших данных.
- `scripts/backup/` — бэкап (обе базы + фото + документы + `certs/`).
- `scripts/archive_fixes/`, `scripts/archive_migrations/` — отработавшие
  разовые правки и миграции, оставлены для истории.

`backup_db.py` в корне — ручная утилита на случай, когда нужна только
база, без фотографий и документов.

## Наблюдение за сбором данных

Показания идут через вкладку Chrome на заводском компьютере, и это
самое хрупкое место системы: по этим же данным считаются простои и
исправность. Сервер различает два состояния — «расширение не на связи»
(запросов нет вовсе) и «панель не отвечает» (запросы идут, данных в них
нет), — и когда сбор стоит, страницы пишут «нет данных с 14:32» вместо
последних известных значений.

Перерывы пишутся в журнал (`sensor_outages`), история видна в
«Аналитике». Пороги и адресаты уведомления — в «Настройках», карточка
«Наблюдение за датчиками»: тишина считается с 10 минут, уведомление
уходит после 30, одно на перерыв, с 20:00 до 8:00 не отправляется —
утром уходит одна строка.

Выключатель `ACAI_PUSH=0` запрещает отправку уведомлений целиком. Он
нужен, когда сервер поднимают на КОПИИ боевой базы: в копии лежат
настоящие подписки живых людей.

### Свёртка показаний

Сырые показания идут по 19 тысяч в сутки. Три уровня хранения
(`monitoring.db`):

| что | как долго | таблица |
|---|---|---|
| сырые, как пришли | 30 суток | `sensor_readings` |
| минуты: среднее, минимум, максимум | год | `sensor_minutes` |
| часы: то же | навсегда | `sensor_hours` |

Минимум и максимум хранятся рядом со средним нарочно: всплеск внутри
минуты не должен исчезать при усреднении. Часы собираются ИЗ МИНУТ,
поэтому после удаления сырых остаются теми же.

Ночью в 03:30 (через полтора часа после бэкапа)
`scripts/sensors/rollup_sensors.py` сворачивает все прошедшие дни и
сверяет каждый: число минут, число показаний, суммы, минимумы и
максимумы по каждому регистру. Итог — в `rollup_log`.

**Сырые удаляются только после сверки и только если это разрешено**
настройкой `sensors_rollup_autodelete` (по умолчанию выключено). Без
сегодняшней копии базы удаление не выполняется вовсе: сырые показания
не восстановить ничем, кроме бэкапа.

Отчёт сверки за любой день глазами человека:

```bash
./venv/bin/python scripts/sensors/rollup_sensors.py --report 2026-09-10
```

Настройка `sensors_keep_raw_on_alarm_days` («беречь дни, когда
поднимался аварийный флаг») выключена намеренно: флаг 1658 поднят
почти треть суток, и пока неизвестно, что это за сигнал — включённое
вслепую правило означало бы, что сырые не удаляются никогда.

### Ключ датчиков: переходный период

Ключ `acai_sensor_key_2026` лежал прямо в коде расширения — с ним любой
в заводской сети мог писать в историю датчиков. 28.09.2026 он заменён
на случайный, и теперь его вводят в окне расширения.

Пока версия 5 осталась хотя бы на одном компьютере, сервер принимает
оба: `SENSOR_PUSH_KEY` (новый) и `SENSOR_PUSH_KEY_OLD` (старый). Каждое
обращение старым ключом отмечается временем, и в «Настройках» видна
строка «Старый ключ ещё в ходу» с датой. Когда строка сменилась на
«больше не используется», `SENSOR_PUSH_KEY_OLD` убирают из `.env` — по
факту, а не по памяти.

Логина и пароля панели на сервере больше нет: `ACAI_WEBHMI_LOGIN` и
`ACAI_WEBHMI_PASS` убраны из `.env` 28.09.2026. Серверный сбор выключен
и из облака до панели в заводской сети не достучаться, а автовход
делает расширение — своими, введёнными на месте.

## Ждёт решения по данным

Код поправлен, а сами записи в боевой базе — нет: их правит человек, и
угадывать за него нельзя.

- **Генератор тепла 1500 CSD — без этапа** (28.09.2026). У остальных
  семи станков этап исправлен со слов на ключ по списку владельца
  (`scripts/archive_migrations/migrate_equipment_stage_keys.py`,
  журнал — 7 записей). У генератора в базе записано «Сушка /
  Углесушка», а это два разных этапа, и владелец спрашивает у цеха,
  к какому он относится.
- **Пять станков с пустой службой** — Дробилка DTE 117, Дезинтегратор
  PL 601, Смеситель СМК 126, Экструдер MAGNA 575, Генератор тепла 1500
  (28.09.2026). Причина: та же форма службу не спрашивала, а сервер
  писал всё, что пришло, — каждое «Сохранить» её стирало. Сейчас поле
  не стирается и такие станки видны обеим службам с пометкой, но кто за
  них отвечает, решают главный механик и главный энергетик.

## Решено сделать, но ещё не сделано

Здесь то, что владелец утвердил, но отложил. Порядок не обязателен.

- **«Требует привязки»** — раздел с задачами на несвязанное, после
  регистров (владелец, 25.09.2026). Порядок важности: регистры
  датчиков, график ТО, документы, остальное. Адресат по делу: регистры
  — гл. инженеру, ТО и документы — гл. механику или энергетику по
  службе станка, регламенты — технологу.
- **Кнопка «по графику не обслуживается»** для станков без ТО
  (владелец, 25.09.2026). Условия: причина обязательна, запись в
  журнал изменений, отдельный список таких станков — решение должно
  быть видно и его можно пересмотреть, молча прятать нельзя.
  **Исключение: для сосудов под давлением и подъёмных механизмов
  кнопка недоступна.**
- **Заведение документов с диска** — одной кнопкой на станок, но со
  списком файлов, где можно снять галочку с лишнего; по умолчанию
  отмечено всё (владелец, 25.09.2026).
- **Ночная проверка связности и выгрузка карты связей в Excel** —
  после «Требует привязки».
- **Ручная привязка папки к станку в «Документации»** (владелец,
  25.09.2026). Сейчас папка привязывается к станку автоматически и
  только при точном совпадении названий — остальные 442 файла лежат
  в группе «Без привязки к станку». Угадывать нельзя, но человек,
  который знает цех, привязать может. Право — главному механику и
  главному энергетику, прямо на странице «Знания».
